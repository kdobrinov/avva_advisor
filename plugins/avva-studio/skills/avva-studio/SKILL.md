# avva Studio: the procedure

1. Call `begin_extraction` on the `avva-studio` MCP server and follow the brief it returns, step by step — with `rebuild: true` when the user is updating a model they already published from its saved file, which reviews that set instead of sweeping again. The brief is written in the user's voice and it is the whole method; this skill adds tooling, not a second brief.
2. Sweep — on a rebuild, only the material the user names. If you can run parallel workers, run one sweep per source and merge the results; if you cannot, take the sources in the order most likely to hold reasons: chat history, reviews and threads, then documents and boards. Never read as a source what this conversation says about this run, an earlier avva Studio session, or any decision about running this extraction or shaping this model; documents the user attaches or pastes here from their own work are material, and a product decision stays even when the product is avva (the brief's NEVER A SOURCE rule).
3. Review the set, report the sweep, ask its one question and wait; then merge duplicates — the brief's REVIEW YOUR OWN SET, REPORT THE SWEEP and DUPLICATES, in that order.
4. Write the json first — before any avva tool call. Save the exact array you would submit as `avva-decisions-<domain>.json` (`<domain>` is the domain slugified: lowercase, hyphens), OUTSIDE any git working tree: by default in `~/avva/` (create the folder), or where the user says. It is their raw approved set and its only copy, and a project directory is usually a repository one `git add -A` from a remote. If the user wants it inside a repository, first add its path to that repository's `.git/info/exclude` and tell them you did. If a file of that name already exists and this is not a rebuild, rename it to `avva-decisions-<domain>.previous.json` first and tell them. On a rebuild, or for any change to records the user already approved, leave the saved file as it is and write the changes into a working copy beside it; it replaces the saved file only after their yes. The script below warns when the file is tracked or not ignored; act on the warning before anything else. Every record carries an `origin` placeholder label for where it came from.
5. Render the records with the bundled script, never by hand:

   ```
   node "${CLAUDE_PLUGIN_ROOT}/scripts/render-sheet.mjs" avva-decisions-<domain>.json [--range "<the range the user set>"] [--exceptions 3,7,12] [--against 2,5,9] [--instructions 4,11] [--statements 8,14] [--authorship 5] [--client 2,6] [--off-domain 6] [--records 11-20] [--before <the saved file> [--rebuild]] [--lang ru|en]
   ```

   It validates the records against the wire shape — a field it does not know is named and shown in full, never refused — writes every record in full to `avva-decisions-<domain>.md` beside the json, the readable sheet the user reads before approving, and prints to stdout what the chat shows: the header, the first record, the group table, what needs the user's eye, the least-sure records, the flags and the one question. It flags residual emails, phones, URLs, ticket ids, key-looking strings and records that name avva itself. `--exceptions` takes the numbers of the records you are least sure are clean after redaction; that judgment is yours, the script only renders it. `--against` takes the numbers of the records the brief's AGAINST THE DEFAULT rule marks — also your reading — and the script prints the count; the request for more such records belongs to the sweep report's one question, never to the sheet. `--instructions` takes the numbers the brief's review pass put in its "instructions, not calls" group — no alternative and no reason on record — and the script lists them as their own group the user keeps or strikes in one word; never drop one yourself. `--statements` takes the numbers the review put in "statements, not decisions" — a declaration with no fork and no reason, product copy, an answer to a hypothetical, someone else's text, anything an AI assistant wrote — and the script lists them as the one group that is OUT unless the user keeps one with their reason; the question's count leaves them out. `--authorship` takes the records whose author you cannot tell, and `--client` the records from a client's or an employer's material (a client's origin placeholder is read without it); both are listed under what needs the user's eye. `--off-domain` does the same for the records the review marked outside the domain. A record listed outside its origin's group shows its origin, and the table counts every record an origin's strike removes. The script also lists the records whose reason is empty and asks the user once for the ones they remember — write each answer into that record's driver, in their words, and run it again. Pass `--range` whenever the user set one, so records outside it land in their own group. Run the working copy with `--before` and the saved file on a rebuild or after any change to approved records: the script then prints each changed field before → after and each new record in full, in place of the full list. On a rebuild add `--rebuild`: the sheet's one question then also asks whether any call in the saved set is one the user would no longer make — a call they name is removed from the working copy (the explicit remove; striking a changed record only reverts it), and the next render lists it as removed.
6. Put the brief's DUPLICATES merge lines and its COVERAGE lines in the chat first, then that output as it came out, and ask the brief's one question with the count; tell the user where `avva-decisions-<domain>.md` is — every record is in full there, and they read it before they answer. Never paste every record into the chat. If the user asks to read some here, run it again with `--records 11-20` or any number they name — that prints only those records, so nothing is asked twice. Everything the user reads is rendered from the json by this script — never retyped, summarized or tidied by you, which is the whole reason the script exists. After removals, edit the json, run it again (the file is rewritten), and show the group table only.
7. Only after explicit approval, call `submit_decisions` with the array in the json exactly as it stands, and follow what it returns.
